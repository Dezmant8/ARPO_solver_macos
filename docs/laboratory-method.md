# Подготовка лабораторной и отчёта

Этот файл помогает составить промпты и независимые проверки. Он не загружается агентом автоматически. Основание — предоставленные пользователем «Список заданий_1_v1.pdf» и пример «EcoLab1.pdf». PDF не включены в репозиторий.

По уточнению пользователя лабораторные относятся к старой версии Eco. Пример отчёта задаёт образец оформления, но не подтверждает совместимость своего кода с новым SDK. В комплекте `Eco.Framework_20260918.zip` есть базовые интерфейсы ACOM и библиотеки `Mac/arm64`. Сигнатуры, типы, фабрики и правила сборки берите из выбранной версии SDK; требования конкретной задачи проверяйте отдельно. Старые компоненты `EcoCalculatorA/B/D/E` не добавляются в зависимости автоматически по одному лишь примеру отчёта. Обе версии промпта должны работать с одинаковыми SDK и исходным шаблоном; версия SDK фиксируется в отчёте.

## Предмет проверки

В списке заданий требуется новый компонент ACOM, а не только функция на C. Для выбранного варианта необходимо задать его интерфейс, сигнатуры, IID/CID, создание, управление ссылками, сборку и консольный клиент. Для нескольких алгоритмов предусматриваются отдельные компоненты и выбор алгоритма в клиенте. Для большинства численных задач нужны методы для требуемых числовых типов. Сортировки сравнениями имеют универсальный интерфейс вида qsort с void* и компаратором.

### Архитектура до генерации алгоритма

Новые проекты получают общий каркас ACOM версии 2. Он не копирует глобальный экземпляр:
конструктор явно получает зависимости через QueryInterface/QueryComponent, передаёт
необходимые ссылки объекту, освобождает временные ссылки и обрабатывает отказы. Любое
неподдерживаемое агрегирование отклоняется. Исходные публичные IID поставляет eco-wizard;
генератор не меняет их и не редактирует файлы SDK.

До изменения контракта `lab-init` выполняет `checks/acom.c` и сохраняет `acom-preflight.json`.
Проверяются единый IEcoUnknown, переходы между исходным интерфейсом и IEcoUnknown,
время жизни, баланс ссылок, ошибки системы/шины/allocator и памяти. Этот же клиент
включается в проверки каждого ответа модели. Это проверка базового каркаса, а не
доказательство соблюдения всех правил COM произвольным новым компонентом.

До эксперимента спроектируйте минимальный необходимый публичный интерфейс. Если нужны
несколько интерфейсов, дополните независимую матрицу переходов всеми IID, проверьте
возврат одного IEcoUnknown из каждого интерфейса и удержание объекта каждой ссылкой.
Запрет изменения опубликованных IID, порядка методов и сигнатур относится к обеим веткам.
Расширение опубликованного контракта требует нового IID. Одних тестов алгоритма недостаточно.

На Apple arm64 `long` имеет 64 бита, а `long double` совпадает по представлению с `double`.
Это [свойство ABI Apple](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms).
Записывайте фактические типы и точность платформы в контракт и отчёт; наличие метода
long double само по себе не означает дополнительную точность на Mac.

Запреты libc, сторонних библиотек и стандартного выделения памяти относятся к реализации компонента. Способ работы с памятью и типами нужно согласовать с реальным SDK. Для эталонного сравнения в отчёте используются стандартные аналоги C или MATLAB, если это требуется для варианта. Скрининг исходника регулярным выражением не доказывает соблюдение запрета — нужны просмотр кода, сборка и проверка зависимостей. Простой check_abs.py проверяет только демонстрацию окружения.

## Два промпта

Сначала определите одну задачу и одинаковые критерии для обоих решений. Передайте каждому запуску одну исходную папку проекта. В кратком промпте опишите задачу и минимальный необходимый контракт. В подробном раскройте алгоритмы, типы, точность, ограничения, границы и ожидаемые артефакты. Заготовка — examples/prompts/acom-detailed-template.txt. Не запускайте её, пока не заменены квадратные скобки.

Не дополняйте системный промпт скрытым содержанием подробной версии: это убирает исследуемое различие. Проверки одинаковы и задаются до генерации. Когда краткий вариант требует уточнений, продолжайте его через resume — эти запросы, токены и активное время будут добавлены к его первоначальным метрикам. Для ручных уточнений лучше вести отдельные серии run/resume, а автоматический experiment использовать для сравнения при одинаковой автоматической обратной связи.

Одинаковый `CODING_STYLE.md` входит в начальный контекст обеих веток и учитывается в токенах.
Он задаёт архитектурные правила и читаемость: содержательные имена, единое оформление,
короткие функции, одна операция на строку и краткие комментарии о владении ресурсами
и нетривиальных решениях. В нём нет алгоритма лабораторной. Подробный промпт отличается
деталями задачи, а не дополнительными требованиями качества только для одной ветки.
Стиль проверяет управляющий агент; автоматически прошедшие тесты не проверяют читаемость.
Уточнения по читаемости получает локальная модель в той же попытке. Ручная переработка
измеряемого исходника скроет стоимость получения готового решения и не допускается.

Общий каркас ACOM, фиксированный ABI и клиент можно подготовить заранее, но этот объём
нужно явно назвать в отчёте. В примере abs модель пишет только пять численных методов;
метрики не показывают стоимость создания всей фабрики и клиента с нуля.
Перед измерением скомпилируйте незавершённый каркас с `--compile-only`, чтобы ошибка
контракта не попала в расходы на исправление алгоритма. В независимых тестах сообщайте
название каждого проваленного случая, вход, полученное и ожидаемое значения.
UBSan помогает выявлять знаковое переполнение; измеряйте скорость также отдельной сборкой
без него. Интерфейсы и тесты должны быть одинаковыми для двух вариантов.

## Отчёт о лабораторной

README лабораторной содержит прямые относительные ссылки на алгоритм каждой реализации,
публичные интерфейсы, объект, фабрику, консольный клиент, независимые проверки и единый отчёт.
Используйте подписи «вариант с кратким промптом» и «вариант с подробным промптом».
Ссылки на общий незавершённый seed отделяются от ссылок на фактические результаты.
Генерируемый блок показывает статусы всех повторов; провал не называется рабочим решением.

Разделы примера EcoLab1: алгоритм, оценка сложности, улучшения, результаты тестирования, поддержка других компонентов и визуализация. Сведения об агрегировании/включении и callback визуализации включайте, когда они действительно реализованы и нужны вашей работе. Они не добавляются в код каждой темы автоматически по примеру другой лабораторной.

Список заданий требует исходники и сборку, консольный клиент/UnitTest, документ Word с описанием компонента и сравнением вычислений со стандартными аналогами до заданного числа знаков. Для перечисленных в задании сложных разделов дополнительно нужны реальные замеры производительности алгоритма. Личная сквозная проверка итогового кода остаётся частью работы студента.

Отдельный раздел исследования ИИ содержит оба исходных промпта, их размеры, модель и ревизию, параметры, число попыток, уточнения, токены, активное время, успешность и ограничения эксперимента. Отчёт обёртки даёт эти измерения, но не может вывести математическую точность из уверенности модели или автоматически подтвердить все свойства ACOM.

Заполните report-notes.toml по фактическому решению. Если есть CSV с результатами вычислений/замерами, включите его через --benchmarks. Не заменяйте время сортировки временем генерации исходника: первое измеряет алгоритм, второе — процесс разработки с ИИ. При неуспешном варианте покажите провал и затраченные ресурсы; не объявляйте его дешёвым рабочим решением.
