# ARPO Lab для macOS

Окружение для лабораторных ACOM на C89 и сравнения краткого и подробного промпта. Локальная
бесплатная Qwen создаёт код через Apple MLX. Обёртка сохраняет запросы, точные токены, время,
проверки и исправления. Для одной темы создаются два независимых решения и три Word отчёта:
краткий вариант, подробный вариант и общее сравнение. Eco Harness не требуется.

Основная модель — **Qwen3-Coder-30B-A3B-Instruct-4bit**: около 17,2 GB весов, Apache 2.0.
[MLX веса](https://huggingface.co/mlx-community/Qwen3-Coder-30B-A3B-Instruct-4bit),
[исходная Qwen](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct).
Проверенная ревизия `6e302ea604ad9ab206367e2c501d1571023e7b6d` фиксируется установщиком.
Код обёртки распространяется по MIT; Eco SDK пользователь получает отдельно у преподавателя.
[Результаты реальной проверки среды](docs/verification.md) показывают оба прошедших варианта
и все затраты на их исправления. Это техническая проверка одной пары.

## Что нужно скачать

1. Репозиторий — через Git или кнопкой GitHub **Code → Download ZIP**. Распакуйте его.
2. Папку преподавателя **Design operating systems**. Распаковывать её внутренние ZIP вручную не нужно.
   Должны присутствовать `Eco.Framework*.zip` и ZIP `eco-wizard` для **macOS arm64**.
   Проверенный комплект: Framework от 18.09.2026 и eco-wizard 0.2.2.

Основной сценарий — **Apple Silicon (M1 и новее), macOS 14+**
([требования MLX](https://ml-explore.github.io/mlx/build/html/install.html)). Проверенный Mac имеет **48 GB RAM**.
Для основной модели установщик проверяет наличие хотя бы 32 GB; работа на 32 GB не проверена,
а фактическая память зависит от контекста. Для 8–24 GB выберите меньшую модель явно — пример ниже.
Рекомендуется 30 GB свободного места для основной модели, Python и результатов.
MLX профиль не работает на Intel; совместимый внешний API можно настроить отдельно.

VS2010, Linux GCC, QEMU и Eco Harness из учебных материалов для этого сценария устанавливать не нужно.
Полный Xcode для консольной сборки не нужен: используется штатный clang из Apple Command Line Tools.

## Первый запуск

Откройте Terminal в распакованной папке репозитория. Если инструменты Apple ещё не установлены:

```bash
xcode-select --install
```

Дождитесь завершения системного окна установки. Затем из корня репозитория выполните:

```bash
bash scripts/bootstrap.sh
```

Если учебная папка находится в другом месте:

```bash
bash scripts/bootstrap.sh --eco-dir "/путь/к/Design operating systems"
```

Эта команда:

- подготавливает Python 3.13 и `.venv` с MLX и генератором Word отчётов;
- при необходимости скачивает [uv](https://docs.astral.sh/uv/getting-started/installation/) локально
  в `.tools`, без изменения shell профиля;
- подключает публичные заголовки Eco и библиотеки Mac/arm64 в `.eco`, сохраняет SHA256 архивов;
- подключает `eco-wizard` из вашей учебной папки;
- генерирует, собирает в C89 и запускает настоящий тестовый компонент ACOM;
- скачивает выбранную Qwen в `models/qwen-coder` и фиксирует ревизию.

Сначала нужен интернет для Python/пакетов/весов. После подготовки модель и Eco работают локально.
Повторный bootstrap использует существующие SDK и полные веса. Настройки лежат в `.eco/install.json`
и `.eco/model.json`; не переносите эти абсолютные пути с другого Mac. SDK и веса не попадают в Git.

Для ноутбука с меньшей памятью:

```bash
bash scripts/bootstrap.sh --model mlx-community/Qwen2.5-Coder-7B-Instruct-4bit \
  --destination models/qwen-7b
```

Это другая модель: качество проверьте на своей теме, а выбор зафиксируйте в отчёте.
Опции установщика: `--revision`, `--destination`, `--skip-model`, `--skip-smoke`;
`ARPO_PYTHON=3.13` задаёт Python для uv. `--skip-model` полезен разработчику с готовыми весами
или отдельным API, но не заменяет загрузку для первого обычного запуска.
Не меняйте модель между двумя ветками сравнения.

## Выполнить лабораторную через агента в новом чате

В корне есть **[AGENTS.md](AGENTS.md)** — полные инструкции для Codex или другого агента,
который умеет читать файлы и выполнять команды в репозитории.
Откройте именно этот репозиторий в агенте и напишите, например:

> Выполни лабораторную на тему «Сортировка слиянием». Сравни краткий и подробный промпты,
> подготовь два решения и Word отчёты по AGENTS.md. Автор: …, группа: … .

Агент определит требования темы, подготовит единый интерфейс и независимые тесты,
составит два промпта, запустит **локальную Qwen через обёртку**, проверит результаты и
заполнит отчёты по фактическому коду. При неопределённости темы/алгоритма он уточнит необходимое.
Для этой подготовки и анализа нужен внешний управляющий агент, например Codex;
его собственные запросы не учитываются в метриках локальной Qwen и могут иметь отдельную цену.
Локальная модель не получает исходный PDF со всеми заданиями или инструкции нового чата.
[Справочник 77 тем](docs/topics.md) предназначен управляющему агенту.
Качество Qwen зависит от темы и промпта. Проект проверяет полученный код и учитывает исправления;
автоматическое прохождение любой из 77 лабораторных с первого ответа не гарантируется.

## Проверить весь цикл на готовой постановке

Есть встроенная **постановка задачи 23**, абсолютное значение: настоящий компонент ACOM с пятью
числовыми типами, фабрикой и консольным клиентом. Общий каркас ACOM и клиент поставляются
в seed; Qwen пишет пять численных методов в `SourceFiles/AbsMethods.c`.
Готового алгоритма в seed нет. Такое разделение фиксируется в отчёте: стоимость генерации
численных методов нельзя выдавать за стоимость создания всего компонента с нуля.
Внешний эталон проверяет точность, signed zero, крайние целые, null указатели и управление ссылками.
Проверка использует UBSan для выявления неопределённого поведения C. Для отдельного сравнения
скорости алгоритмов выполняйте замер без санитайзера и указывайте параметры сборки.

```bash
bash scripts/arpo lab-init --directory labs/abs --topic "Абсолютное значение" \
  --name Eco.LabAbs --example abs
bash scripts/arpo lab-run labs/abs --repeats 1
```

`lab-run` сам запускает MLX, прогревает его, выполняет оба варианта и останавливает собственный
сервер. Уже работающий сервер с той же моделью сохраняется. Одна пара нужна для проверки среды;
для исследования используйте `lab-run labs/abs` — по умолчанию три пары с чередованием порядка.
Не создавайте заново существующую папку: `lab-init` откажется перезаписать прошлую лабораторную.
Qwen может ошибаться и потребовать уточнения. Если вариант получил stalled, прочитайте диагностику
в run.json и продолжите через lab-resume. Для этого примера есть тексты уточнений
[null и signed zero](examples/prompts/abs-correction-null-zero.txt) и
[переполнение целых](examples/prompts/abs-correction-overflow.txt). Применяйте их по фактической
ошибке; сохранённый run-ID указывается в команде. Эти уточнения увеличивают его итоговую стоимость.

Все результаты лежат внутри `labs/abs`:

```text
labs/abs/
├── lab.json, task.md, config.toml
├── short.txt, detailed.txt
├── notes-short.toml, notes-detailed.toml, notes-comparison.toml
├── checks/                  независимые проверки, недоступные файловым инструментам модели
├── seed/Eco.LabAbs/          одинаковый исходный проект для обеих веток
│   ├── .sdk/                копия выбранного SDK, только чтение
│   ├── .arpo-build.py        сборка через clang, только чтение
│   └── SourceFiles/, SharedFiles/, HeaderFiles/, UnitTestFiles/, AssemblyFiles/
├── runs/experiment-…/       две run папки на каждый повтор, журналы и workspace
└── reports/experiment-…/
    ├── comparison.docx      общий сравнительный отчёт
    ├── short/comparison.docx
    └── detailed/comparison.docx
```

В каждом каталоге отчёта также создаются Markdown, HTML, CSV и JSON. Метрики и тексты промптов
попадают туда автоматически. Описание алгоритма, сложности, точности и выводов нужно заполнить
в `notes-*.toml` после просмотра фактических решений; это делает управляющий агент либо студент.
Первый автоматический документ с незаполненными полями — заготовка, а не готовый отчёт для сдачи.
После заполнения пояснений пересоберите документы без новых запросов к модели:

```bash
bash scripts/arpo lab-report labs/abs
```

## Подготовить свою тему вручную

```bash
bash scripts/arpo lab-init --directory labs/merge-sort --topic "Сортировка слиянием" --name Eco.Lab55
```

Перед запуском:

1. Определите контракт методов в `seed/Eco.Lab55/SharedFiles` и требования в `task.md`.
   Для сравнительных сортировок нужен универсальный интерфейс с компаратором по смыслу qsort.
2. Запишите `short.txt` и `detailed.txt`. В seed и системный промпт не помещайте скрытую
   алгоритмическую подсказку из подробной версии.
3. Реализуйте **независимые** проверки в `checks/validate.py` или отдельном эталонном C-клиенте.
   По умолчанию validate.py намеренно отклоняет решение. Проверка своей темы обязательна:
   успешной сборки и тестов, написанных самой моделью, недостаточно.
4. Настройте `config.toml`: проверки, бюджет, число повторов, сведения автора, разрешённые команды.
   Для неизменных контрактов добавьте файлы в `tools.read_only_paths`.
5. Запустите `bash scripts/arpo lab-run labs/merge-sort`, изучите код/проверки и заполните
   три файла `notes-*.toml`, затем выполните `lab-report`.

Сборка отдельного полученного решения:

```bash
# Сначала перейдите в workspace выбранного run:
python3 .arpo-build.py --run
```

Для запуска из Terminal можно использовать Python из `.venv`. SDK заголовки идут как `-isystem`,
студенческие исходники проверяются `-std=c89 -pedantic-errors`. Скрининг символов `nm` ловит
распространённые запрещённые библиотечные вызовы, но не заменяет просмотр кода и зависимостей.
Базовый профиль собирает статический компонент; Xcode проекты сохраняются в `AssemblyFiles/Mac`.
Для Xcode можно задать `ECO_FRAMEWORK` из `.eco/install.json` в Settings → Locations → Custom Paths.
Основной проверенный путь сборки — `.arpo-build.py`, без зависимости от старой версии macOS SDK в Xcode.
Для численных тем учитывайте [ABI Apple arm64](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms):
`long` имеет 64 бита, а `long double` совпадает с `double`. Зафиксируйте это в контракте и отчёте.

Старые примеры лабораторных помогают оформить отчёт. Сигнатуры и типы берите из подключённого
SDK. Не включайте старые CalculatorA/B/D/E в зависимости автоматически по одному лишь примеру.
[Методика](docs/laboratory-method.md) и [заготовка подробного промпта](examples/prompts/acom-detailed-template.txt).

## Уточнить неудачный вариант

Не начинайте его заново, если измеряете стоимость получения рабочего решения:

```bash
bash scripts/arpo lab-resume labs/merge-sort \
  --run labs/merge-sort/runs/experiment-<ID>/<run-ID> \
  --prompt "Исправь обработку пустого массива и размеры элементов"
```

Уточнение добавляется в исходную историю и суммарные метрики. Сервер запускается автоматически,
отчёты обновляются. Если лимит уже исчерпан, увеличение задаётся явно:

```bash
bash scripts/arpo lab-resume labs/merge-sort \
  --run labs/merge-sort/runs/experiment-<ID>/<run-ID> \
  --prompt-file labs/merge-sort/correction-01.txt \
  --add-requests 10 --add-tokens 40000 --add-seconds 600
```

Конфигурация сохранённого run и независимые тесты после старта не меняются.
После трёх подряд одинаковых ответов, не прошедших проверку, запуск получает статус `stalled`.
Все эти запросы остаются в метриках. Дополнительный промпт через `lab-resume` сбрасывает
счётчик повторений и продолжает ту же историю; `agent.max_identical_replies=0` отключает остановку.
Если поправили неверный эталон, проведите новую пару и обозначьте старую как недействительную.
Для сложных тем измеряйте также время алгоритма и эталона; это отдельный показатель от времени ИИ.
Численные CSV (до семи колонок) можно сохранить в `benchmarks-short.csv`,
`benchmarks-detailed.csv`, `benchmarks-comparison.csv` — `lab-report` вставит их в нужные документы.

## Что можно настроить

Все настройки каждой темы находятся в `labs/<тема>/config.toml`. Полный справочник —
[docs/configuration.md](docs/configuration.md). Можно менять модель/API, параметры генерации,
системный промпт, бюджеты, инструменты, окружение процессов, таймауты, независимые проверки,
число повторов/порядок и сведения отчёта. CLI параметры `--config` и `--model` ставятся перед подкомандой.
Для эксперимента обе ветки используют одну конфигурацию; изменяется только пользовательский промпт.

Профиль ACOM по умолчанию использует `agent.protocol="files"`: модель возвращает полные
изменённые файлы, обёртка собирает и проверяет их после каждого ответа, затем передаёт
диагностику для исправления. Это позволяет проводить эксперимент без навигационных
запросов модели. Для инструментального цикла доступны `native` и `blocks`; для одного файла
есть `single-file`. Специальный `qwen-xml` разбирает XML из сырых token ID MLX и требует
локальный токенизатор Qwen. Подменять протокол внутри уже начатого run нельзя.

В обе ветки включается одинаковый выбранный контекст: список файлов и незавершённые исходники
шаблона Eco. Настройки `agent.workspace_manifest` и `agent.context_files` управляют этим
контекстом. Его токены учитываются; готового алгоритма и PDF заданий там нет. В примере abs
используется `single-file`, начальный контекст ограничен контрактом методов.

Системные пути не нужно прописывать в `.zshrc`. Для проверки только Eco:
`bash scripts/arpo eco-doctor`. Для отдельного запуска сервера:
`bash scripts/arpo --model "$PWD/models/qwen-coder" serve`.
`lab-run --no-server` использует уже запущенный API. Для другой модели/порта запишите их в config.toml.
MLX запускается с отключённым общим prompt cache; прогрев не входит в измерения решений.

## Что измеряется

| Метрика | Значение |
| --- | --- |
| requests | Все попытки HTTP генерации, включая сетевые ошибки и ретраи |
| successful_requests / failed_requests | Полученные валидные ответы / ошибки |
| prompt_tokens_known | Сумма входных токенов из `usage`, включая историю и системный промпт |
| completion_tokens_known | Сумма выходных токенов из `usage` |
| tokens_complete | Есть ли достоверный `usage` у каждой попытки |
| active_time_s | Полное активное время агента: API, инструменты, проверки, паузы ретраев |
| model_time_s | Время ожидания HTTP ответов, включая обработку и передачу |
| tool_time_s / validation_time_s | Время действий агента / независимых проверок |
| elapsed_with_wait_s | Календарное время от создания до последней сессии, с паузами студента |
| user_followups | Сколько уточнений отправил пользователь через resume |
| repair_cycles | Автоматические исправления после ошибки протокола или провала проверки |
| estimated_cost_known | Тарифная стоимость известной части токенов; по умолчанию 0 |

Количество запросов к ИИ и количество сообщений пользователя — разные показатели. Один промпт запускает несколько запросов инструментального цикла. В журнале сохраняется размер исходного промпта в символах/байтах; входные токены первого запроса также включают неизменный системный промпт и шаблон модели.

Обёртка не оценивает токены по длине текста. Если сервер не возвращает `usage`, при `require_usage=true` запуск останавливается, сохранив попытку. Для сетевой ошибки токены неизвестны, поэтому известная сумма — нижняя граница, а не точный итог. CSV/JSON сохраняют этот признак, отчёты помечают неполные суммы звёздочкой. Локальная модель не оплачивается по токенам; электричество и стоимость оборудования автоматически не измеряются.

Лимиты запросов и времени учитываются по всем сессиям запуска. Лимит токенов проверяется между ответами, поскольку реальный размер входа известен из `usage` после ответа; последний запрос может превысить лимит. Контекст не обрезается скрытно: превышение `max_context_chars` останавливает запуск. Режим `native` использует штатный tool calling: write_file/read_file/list_files/run_command/finish. Для моделей без него можно выбрать `agent.protocol="blocks"`: исходники передаются буквальным текстом в блоках `file:<путь>`, а команды и статус — небольшим JSON блоком. Старый формат с `write.content` также поддерживается.

В однофайловой демонстрации и ACOM примере abs используется `agent.protocol="single-file"`: модель возвращает один полный блок кода, который сохраняется в `agent.fallback_file` и проверяется. Для native можно отдельно включить fallback_file, чтобы также принимать единственный обычный блок C кода в текстовом ответе. Несколько альтернативных блоков приводят к запросу исправить формат. Для лабораторной с несколькими изменяемыми файлами оставляйте fallback пустым и выбирайте files, native или blocks.

## Честное сравнение

Используйте одинаковые модель и её ревизию, параметры, SDK, системный промпт, инструменты, бюджет и независимые тесты. Меняйте только пользовательский промпт. Один повтор подходит для проверки настройки, для отчёта используйте не менее трёх и рассматривайте разброс вместе с медианой. При `alternate` порядок чередуется: краткий → подробный, затем подробный → краткий.

При фиксированном seed повторения оценивают прежде всего разброс времени; ответы могут совпасть. Для оценки разных случайных генераций сделайте отдельные парные серии с разными seed и одинаковым seed внутри каждой пары. Подробный демонстрационный промпт содержит алгоритмическую подсказку для отрицательного нуля: учитывайте это при интерпретации сравнения. Он меняет содержание инструкций вместе с их длиной, поэтому пример не измеряет изолированный эффект числа символов.

`serve` отключает общий prompt cache (`--prompt-cache-size 0`), чтобы сравнение включало полную обработку входа каждой ветки. По умолчанию сервер использует последовательную генерацию без дополнительной квантизации KV, с `--prefill-step-size 512`; дополнительные флаги после `--` могут переопределить значения. Общие параметры клиента соответствуют [рекомендациям автора Qwen](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct): temperature=0.7, top_p=0.8, top_k=20, repetition_penalty=1.05. В ACOM примере abs штраф повторений явно отключён (`1.0`); эта настройка одинакова для обеих веток и сохраняется в отчёте. Прогрев перед экспериментом записывается отдельно в warmup.jsonl и не входит в измерения решений. Запускайте эксперименты последовательно и закрывайте приложения, нагружающие GPU. Даже temperature=0 и seed не гарантируют одинаковую скорость или побитовую воспроизводимость на другом железе.

Статус `passed` означает прохождение настроенных проверок, `unverified` — модель закончила, но независимых проверок нет. Другие статусы: `stalled`, `budget_exhausted`, `context_limit`, `api_error`, `interrupted`, `error`. Эксперимент возвращает ненулевой код, если хотя бы одна ветка не прошла проверки, но сохраняет все результаты. Не называйте результат рабочей лабораторной только по уверению модели.

## Настройка

Все параметры по умолчанию находятся в `src/arpo_lab/config.py`. TOML может задавать только изменяемые поля; неизвестное имя считается ошибкой. `--config` и `--model` стоят **перед** подкомандой. Подробный справочник: [docs/configuration.md](docs/configuration.md).

| Раздел | Что можно менять |
| --- | --- |
| model | Модель/локальные веса, API URL, таймаут, параметры генерации, seed, ретраи, usage, секрет через env, дополнительное тело запроса |
| agent | Протокол, системный промпт, общий контекст seed, лимиты запросов/токенов/времени/действий/контекста |
| tools | Исполнение команд, защищённые пути, точный список исполняемых файлов, sandbox, таймауты, размер файла/папки/вывода/листинга, окружение процессов |
| validation | Независимые команды, таймаут, размер обратной связи |
| experiment | Число повторов, порядок, прогрев |
| pricing | Тарифы за миллион входных/выходных токенов, валюта |
| report | Название, автор, группа |

Другие модели и настройки сервера:

```bash
bash scripts/arpo --config configs/small-model.toml serve
bash scripts/arpo --model mlx-community/Qwen2.5-Coder-14B-Instruct-4bit serve
bash scripts/arpo --model "$PWD/models/qwen-coder" serve -- --kv-bits 4 --prefill-step-size 512
```

Параметры кеша, KV quantization и speculative decoding влияют на измерения. `serve` сохраняет команду в `.cache/arpo-server.json`; для совпадающих локальных модели и порта она включается в run.json и отчёт. Это сохранённая конфигурация запуска, не опрос активного процесса. Для стороннего сервера запишите команду самостоятельно. Настройки сервера и клиента должны указывать одинаковую модель и порт. Подключение LM Studio, llama.cpp и другого совместимого сервера: задайте `model.base_url`, `model.name` и проверяйте наличие `usage`. Для сервера на другом компьютере нужно явно установить `allow_remote=true`. Ключ указывается через переменную `ARPO_API_KEY`; в журнал заголовок Authorization не записывается.

## Отчёт

`report` создаёт `comparison.md/html/csv/json`, а с `--formats ...docx` — Word. JSON содержит все исходные метрики, CSV удобен для своих графиков; HTML открывается без интернета и печатается в PDF средствами браузера. В сравнении выводятся медианы всех попыток, доля успешных и все статусы. JSON также содержит минимум/максимум и медиану активного времени успешных решений отдельно. При разных параметрах или начальных файлах появляется предупреждение.

Шаблон учитывает разделы приложенного примера: алгоритм, сложность, улучшения, результаты тестирования, поддержку компонентов, визуализацию; добавлены сравнение ИИ и воспроизводимость. Заполните `examples/report-notes.toml` своими проверенными объяснениями. Реальные измерения алгоритма и сравнение точности можно передать отдельно через `--benchmarks <CSV>` (до 7 столбцов с заголовком, например случай, эталон, результат, абсолютная ошибка, время). Единицы укажите в названиях столбцов. Время алгоритма не выводится из времени генерации ИИ.

## Файлы и ограничения

```text
runs/experiment-.../
  experiment.json        # порядок, повторы, конфигурация и SHA256 промптов
  warmup.jsonl           # прогрев, исключённый из сравнения
  <run-ID>/
    prompt.txt           # исходный промпт
    followup-01.txt       # уточнение, если было
    run.json             # история, статусы, конфигурация, версии, метрики
    requests.jsonl       # каждая попытка HTTP, тело запроса, ответ, usage, время
    events.jsonl         # файловые действия, команды и проверки
    workspace/           # полученное решение и сборка
```

Файловые инструменты запрещают абсолютные пути, `..` и symlink. На macOS `sandbox=required` запускает команды и проверки под `sandbox-exec`: доступ к workspace и системному toolchain, без сети и чтения Downloads. Агенту передаётся только текст промпта и явно скопированный seed. На системах без sandbox-exec для локальных демонстраций можно выбрать `off`; тогда запущенный код имеет обычные права пользователя и ограничение файловых инструментов его не изолирует. `auto` использует sandbox, когда он доступен. macOS sandbox-exec устарел, профиль может потребовать адаптации под нестандартный компилятор; sandbox не заменяет VM для запуска недоверенного кода. Не помещайте PDF заданий и личные файлы в seed.

Журналы содержат промпты и исходники. `runs/`, `reports/`, веса, кеш, `.env` исключены из Git. Для публикации обезличенных результатов добавляйте только выбранные файлы осознанно. PDF преподавателя автоматически не копируются в репозиторий. Если процесс аварийно завершён и остался статус running, убедитесь, что он остановлен, выполните `bash scripts/arpo recover runs/<ID>`, затем resume; длительность аварийно оборванной сессии может быть неполной.

## Разработка и диагностика

```bash
uv pip install --python .venv/bin/python -e '.[dev,reports]'
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/ruff check src tests examples/checks
```

Тесты обёртки не требуют весов или GPU: проверяют реальные HTTP запросы к тестовому серверу, учёт usage/повторов, цикл исправлений, независимость вариантов, накопление метрик и ограничение путей. CI запускает их на Python 3.11 и 3.13. Зависимости конкретного установленного окружения можно записать командой `uv pip freeze --python .venv/bin/python > requirements-local.txt`; файл со всеми версиями не переносит веса.

`requirements-mlx-macos.txt` фиксирует версии проверенного здесь окружения macOS arm64 / Python 3.13. Это снимок прямых и транзитивных зависимостей; для другого Python/OS используйте установку по pyproject.toml. Чтобы повторить зафиксированные версии в созданном venv: `uv pip install --python .venv/bin/python -r requirements-mlx-macos.txt`, затем `uv pip install --python .venv/bin/python -e .`. Самостоятельная проверка sandbox на Mac: `python scripts/check_sandbox.py`.

Если `doctor` сообщает, что сервер недоступен, сначала запустите `serve` в другом терминале. Ошибка `No Metal device available` в среде с ограничениями доступа означает, что процессу недоступен GPU: запускайте сервер из обычного Terminal. OOM — уменьшите модель, контекст/выход, закройте другие программы или включите квантизацию KV. `sandbox_init: Operation not permitted` означает, что текущая среда запрещает создание sandbox; запускайте из обычного терминала. Провал C89 — читайте вывод проверок и исправляйте решение, сохраняя историю эксперимента.
